The thirty-second narrative

DClaw Marketing began Sprint 1 as a multi-tenant scaffold. By Sprint 2 it had a feature-complete content pipeline. Sprint 3 hardened it into an operator-ready product (admin model, slugs, sidebar, auto-merge). Sprint 4 turned the agent platform from scaffold to runtime: a Model Registry across 26 provider types, role-agents over a resolver chain, generation adapters, AEO, observability. Sprint 5 — the one in flight — is rebuilding /conductor into a real multi-agent orchestration surface with Claude Agent SDK tool use, streaming, research modes, and (as of last week) full decoupling from Anthropic via OpenAI-compatible providers.

What works today

  • Foundation — multi-tenant org/project/campaign hierarchy, 10 RBAC scopes, two-tier admin model, audit, approvals with 4-eye rule, brand kits, knowledge graph, object storage.
  • Content pipeline — Creatives Agent (text shipped, multimedia adapters scaffolded), repurposing engine, A/B variants, hook + headline lab.
  • Publishing — calendar, scheduled posts, 13 channel publishers (X, LinkedIn, IG, FB, YouTube, TikTok, Threads, Substack, Bluesky, Reddit, Pinterest, Discord, Mastodon), email sequences (Resend / Postmark / SendGrid), ads publisher (Meta / LinkedIn / Google).
  • Audience & revenue — Lead 2.0 with enrichment + ID resolution + scoring, two-way CRM sync (HubSpot, Salesforce, Pipedrive, Attio), segment builder, attribution with Sankey view.
  • Agent platform — 8 role-agents (Conductor, Creatives, SMM, SEO, Paid Media, Analyst, Inbox, Reviewer) over a Model Registry with auto-discovery, capability heuristic, health-check beat, and a user→org→pool→env→stub resolver chain.
  • Operability — OpenTelemetry + Grafana + Sentry tags, cost ledger per agent run, trace replay endpoint, lean CI (local tests gate; GitHub does only auto-merge).

What is open

  • Conductor epic (Sprint 5). A through G have all landed in main under the [Unreleased] changelog banner; no tag yet.
  • Pending roadmap items. Brand-Safe Image Editor (B7), SMS/WhatsApp (C5), Push/In-App (C6), Auto-Optimizer bandit auto-promote (G5). All P2 or later in PLAN-v1.2.
  • Health diagnostics. One cosmetic frontend healthcheck failure (host port reachable, only the in-container probe fails), one weak default JWT secret, three Pydantic field-shadow warnings. None are user-visible.
  • Marketing collaterals. Five open issues (#49–#53) for one-pager, slides, demo video, social drafts. Engineering does not touch these.
Headline. Repository in a healthy "between-tagged-releases" state. Sprint 5 Conductor epic is mostly merged. No outages, no open code PRs, no open dev issues. The natural next milestone is a v1.2.0 tag once Sprint 5 wraps the small set of remaining items.
Chapter 2

Recap — Sprints 1 through 4

Five sprints. 217 merged pull requests. Each sprint had a distinct shape. This chapter compresses the prior four into roughly four pages so a returning reader can follow the rest of the document without re-reading four sprint reports.

Sprint 1 — Foundations (closed 2026-05-12, tagged v1.0.0)

47 PRs. The MVP scaffold. What landed: a multi-tenant User → Organization → Project → Campaign → Asset hierarchy with fastapi-users JWT auth, admin-only user creation, mandatory first-login reset; a Celery + Redis background-worker subsystem with SSE-streamed Job rows; S3-compatible object storage (MinIO in dev, S3/R2 in prod) with presigned uploads; an AuditEvent + ApprovalRequest pair backing a 4-eye-rule Approval Inbox; the Brand Kit with versioned palette, fonts, voice sliders, and do/don't-say lists; a Knowledge Graph that ingests URLs, files, Git repos, and ZIPs into pgvector; the Creatives Agent text path; and a Calendar + Scheduler + Repurposing Engine + Variant A/B studio scaffold.

At Sprint 1 closeout the platform looked like a working MVP that one operator could drive end-to-end. The 30-page sprint status PDF (also in obsidian/reports/) was the canonical artefact. Sprint 1 was renamed from v0.1.0-mvp to v1.0.0 in PR #278 so that release tags align with PLAN-v1.2.md.

Sprint 2 — Feature Breadth (closed 2026-05-13, tagged v1.1.0)

112 PRs. The most prolific sprint by raw count. Sprint 2 took the MVP and grew its surface in every direction: eleven new channel publishers, Connection Registry with Fernet-encrypted per-org data keys, an MCP integration hub with 14 concrete adapters (HubSpot, GA4, Stripe, Ahrefs, Webflow, WordPress, Ghost, Slack, Discord, Notion, Google Drive, Salesforce, Mixpanel, PostHog), Lead 2.0 with enrichment + ID resolution + scoring, two-way CRM sync with HubSpot / Salesforce / Pipedrive / Attio, segment builder with AND/OR filter DSL and nightly materializer, first-touch + last-touch + time-decay attribution with a Sankey view, the email + newsletter stack (Resend / Postmark / SendGrid sequences with delay + branch conditions), the Ads Publisher for Meta + LinkedIn + Google Ads (paused-campaign create), and the Webhook Hub (inbound) with Automation rules.

Sprint 2 also added the /admin/audit browser, OAuth scaffolds for seven channels, and the BYO MCP marketplace scaffold. By end of Sprint 2 the platform stopped being a content tool and started being a full-stack marketing operating system.

Sprint 3 — Operator-Ready Hardening (closed 2026-05-14, tagged v1.1.1)

45 PRs over ~29 hours of wall-clock time. Sprint 3 was a hardening sprint with no new product surfaces. What landed: the two-tier admin model (bootstrap superadmin s-admn-000000 plus per-org admins) with centralized guards, last-admin protection, self-demote refusal, audit trail, and in-app notifications on role changes; the universal slug scheme (u-{first4}-{6hex}, o-{first4}-{6hex}, bootstrap hardcoded) with a migration that re-slugs every existing row; a left-sidebar navigation that grouped pages by domain; display_code 6-hex unique handles; an end-to-end auto-merge + auto-close pipeline; the repurposing engine; the hook + headline lab; the F2 content-performance heatmap; signed-JWT embeddable dashboards; the per-org retainer budget model; the H2 blog pipeline for SEO; the per-project Kanban board; and a minimal HTML-body landing-page builder.

Sprint 3 also tightened the docs from 31 to 17 files and made the version line align with PLAN-v1.2 by renaming v0.1.0-mvp → v1.0.0 and v0.2.0 → v1.1.0. Everything in this sprint was about making existing surfaces safe to operate, not adding new product capability.

Sprint 4 — Agents Go Live (closed 2026-05-15, tagged v1.1.2)

22 PRs. Sprint 4 turned the scaffolded agent platform into a running system. Five large lanes:

  • Model Registry & AI Gateway (S4-M, 11 issues). ModelProvider, ModelEntry, ModelCallLog, OrgModelAssignment, UserModelPreference tables (migrations 20260525_0001-0003); 26 provider types spanning Anthropic, OpenAI, Gemini, Vertex, Azure, Bedrock, Mistral, Cohere, Voyage, HF, OpenRouter, Groq, Together, Fireworks, DeepSeek, Perplexity, SambaNova, Replicate, ElevenLabs, Runway, Suno, Deepgram, Cartesia, fal.ai, Ollama, and openai_compatible; auto-discovery + capability heuristic; health-check beat every five minutes; the model_resolver.py chain (user → org → pool → env → stub); a full /admin/models page; ModelSettingsPanel in the Conductor; useModelGate + ModelGateBanner onboarding gate; and an InlineModelSelector on the Creatives Agent.
  • Agent Runtime (S4-A, 5 issues). agents/runtime.py with a resolver-aware run_completion() that hits Anthropic or any OpenAI-compatible endpoint; agents/roles.py with curated system prompts for seven role-agents (creatives / smm / seo / paid_media / analyst / inbox / reviewer); a generic runner at POST /agents/role/{name}/run; services/trust_mode.py for autonomy posture lookup (hard_gate / soft_gate / auto); 4-eye approval with approvers_required + approvers_user_ids_json; reasoning-trace replay at GET /agents/runs/{request_id}/trace.
  • Generation + Cost + Lint (S4-B, 3 issues). services/generation_adapters.py with httpx shells for Replicate / Runway / Suno / ElevenLabs / Cartesia / Deepgram; services/agent_cost.py per-run CostLedger writer with token→USD rates; services/dont_say.py brand-banned phrase lint.
  • Conductor UI (S4-C, 3 issues). Full-screen Conductor view, context-aware dock, per-action model picker.
  • Workflow Runner + Templates + Sandbox (S4-D, 4 issues), Brand Setup Studio backend (S4-E, 3 issues), OAuth + TOTP + Auth (S4-F/G, 2 issues), Observability (S4-H/I, 2 issues), Tech Debt (S4-J, 3 issues), AEO scorer (S4-K, 2 issues).

By end of Sprint 4 every agent in the platform was running on real model calls through a real registry, every run was logged with a USD cost, and every role had a curated prompt. The platform stopped being "agents-in-theory" and became "agents-in-production."

Chapter 3

Project Intent & Target Audience

Who DClaw Marketing is for, what it is supposed to do, and how the project's intent has — or has not — shifted over five sprints.

The stated intent

From PLAN-v1.2.md, verbatim: "DClaw Marketing is an end-to-end product-marketing operating system: one place where a small team (or one operator + AI agents) plans campaigns, generates multimedia content, schedules and publishes across every channel, talks to leads, attributes revenue, and learns. The MCP integration hub is the connective tissue — every external surface (social, ads, CRMs, analytics, drive, design, voice) plugs in as an MCP server so agents can read/write through one consistent permissioned layer."

The north star, also verbatim: "from a single PRD, this app produces a launch — copy, visuals, video clips, ads, landing pages, an email sequence, a scheduled posting plan, and a closed-loop attribution view — with a human approving every external action."

Deployment posture

DClaw Marketing is sold and shipped as a Helm chart plus container images that an operator runs on their own Kubernetes cluster. There is no SaaS dependency, no vendor lock-in, no data leaving the customer perimeter. The MCP layer means every external surface is a pluggable adapter with credentials encrypted at rest per-org with a Fernet master key the operator holds out-of-band.

Dev runs on Docker Compose (Postgres + Redis + MinIO + backend + frontend), production runs on the Helm chart in helm/. Storage swaps from MinIO to S3 / R2 / Spaces. Observability is OpenTelemetry → Grafana with Sentry tags for exceptions. Background work is Celery + Redis. The frontend is Next.js 14 standalone served behind whatever ingress the customer chooses.

Where intent has drifted

Sprint 4's Model Registry + Conductor work has quietly broadened the project's centre of gravity. The bottom half of the codebase — ModelRegistry, agent runtime, cost ledger, approvals, trace replay — is now a general-purpose agent operations substrate that happens to also serve the marketing use case. The marketing-specific layers (publishers, CRM sync, attribution, AEO) sit on top of this substrate and could in principle be lifted away.

This is a fact about the codebase, not a recommendation. It is captured here because any future planning conversation should know that the platform has, without anyone deciding it explicitly, become two products sharing a runtime: a marketing OS and an agent ops platform. The pivot conversation is documented separately in TEMP-pivot-discussion.md; it is intentionally not summarised in this report.

Executive Summary

For non-engineering readers. Where the project is, what it can do, what it is worth, what it costs, and what decisions are owed in the next sixty days.

One paragraph

DClaw Marketing is, as of 16 May 2026, a five-sprint-old, four-release-tagged, self-hosted marketing operating system with a live multi-agent runtime, thirteen channel publishers, four CRM integrations, a full Model Registry across twenty-six provider types, and a Conductor multi-agent UI that has just absorbed Claude Agent SDK tool use, streaming, vision, web search, and OpenAI-compatible provider support. The platform is in good operational shape: stack is up, no outages, no open code PRs, no open dev issues, and the codebase is roughly sixty-seven thousand lines spread across two healthy halves (a 42k Python backend and a 25k TypeScript frontend). The next natural milestone is a v1.2.0 tag once Sprint 5 closes; the strategic question on the table is whether the platform's centre of gravity remains marketing-OS or whether the agent ops substrate beneath it deserves to be a product in its own right.

What the company has, in business terms

A working product

Tagged v1.1.2, deployable today on any K8s cluster, sold as Helm + container images. Self-hosted, no data egress, MCP-first.

An agent platform

Eight role-agents, a Model Registry across 26 provider types, cost ledger per run, approval workflow with 4-eye rule, full reasoning-trace replay.

A breadth moat

Thirteen channel publishers, four CRM adapters, fourteen MCP integrations, three email providers, three ad networks. Replacing this surface is months of work for a competitor.

A clean codebase

Five sprints in, 67k LOC, 40 migrations, 80 backend tests, zero open code issues, zero pending PRs. Tech debt has been actively retired in the S4-J lane.

A defensible architecture

Multi-tenant from day one. Two-tier admin model. Per-org Fernet-encrypted credentials. Audit and approval baked into the data layer, not bolted on.

A reusable substrate

Model resolver chain, cost ledger, approval inbox, trace replay, and Conductor are not marketing-specific. They are an agent ops platform with a marketing skin.

What the company does not yet have

  • Customers on production. There is no production deployment record in the repository; the project's deployment posture is "ready to ship", not "shipped to a paying tenant."
  • The B7 Brand-Safe Image Editor. Pending; deferred to Sprint 5+.
  • SMS / WhatsApp (C5) and Push / In-App (C6) channels. Pending; P2 priority.
  • The Auto-Optimizer bandit (G5). Variant A/B is shipped; auto-promotion has not started.
  • An executive sales narrative. The README and PLAN are strong engineering documents; there is no marketing/one-pager.md yet — issue #49 is open.

Why the Conductor epic matters

Before Sprint 5, /conductor was a planning UI on top of role-agent dispatch. After Sprint 5, it is a full agentic chat surface with: real-time SSE streaming, Claude Agent SDK tool calling, vision input, web search, URL fetch, Quick / Light / Deep research modes, markdown rendering, slash commands, copy + regenerate, voice, thread operations, and full decoupling from Anthropic via OpenAI-compatible providers. It is the most significant single user-facing surface the platform has ever shipped.

The decoupling in PR #370 is, in retrospect, the largest strategic move in Sprint 5: it means the platform is no longer Anthropic-only, even at the Conductor level. Any OpenAI-compatible endpoint — local Ollama, OpenRouter, Together, Fireworks, Groq, DeepSeek — can drive the Conductor today, gated by OPENAI_COMPAT_BASE_URL / API_KEY / MODEL env vars. That is, in business terms, a "no vendor lock-in" claim the platform can now make honestly.

Backend topology

Routes (app/api/v1/) consume services (app/services/) which talk to models (app/models/) and emit jobs to the worker (app/worker/). Agents (app/agents/) sit at the top, calling the Model Registry resolver to obtain a ModelEntry and then dispatching the actual call through either anthropic_client.py or openai_compat_client.py. Every call logs to ModelCallLog via fire-and-forget; every run accrues to CostLedger.

Cross-cutting middleware: quota guards (quota_guard.py, cost_caps.py) sit between the route handler and the service layer; audit hooks (audit.py) write to AuditEvent on every approvable action; the approval queue (approval_request.py) holds the 4-eye state.

Frontend topology

Routes live in frontend/src/app/ organised by domain. ~30 top-level segments. UI primitives in components/ui/ (shadcn-remapped) and brand components in components/dk/. Light mode only, Poppins, --dk-* tokens per frontend/src/styles/brand.css. 43 component files.

The frontend talks to the backend via a Next.js rewrite proxy that resolves BACKEND_INTERNAL_URL at build time so the in-container path goes container→container; the browser fetches via NEXT_PUBLIC_API_URL=http://127.0.0.1:8102 (IPv4-pinned to dodge a Colima IPv6 fallback issue).

Issue 1 — Frontend healthcheck failing (cosmetic)

Symptom. docker compose ps reports dclaw-marketing-frontend-1 as unhealthy despite the host port responding 200.

Cause. The Next.js standalone server.js binds to the container's eth0 IP (172.18.0.7:3015) rather than 0.0.0.0. The Dockerfile's healthcheck — wget -q --spider http://localhost:3015/ — runs inside the container and resolves localhost to 127.0.0.1, which is not where the server is listening. Connection refused.

Fix. Add ENV HOSTNAME=0.0.0.0 in the runner stage of frontend/Dockerfile (one line, before the CMD). This forces Next.js standalone to bind to all interfaces and lets the healthcheck pass without any application change.

Issue 2 — JWT default secret is 31 bytes (dev-only)

Symptom. Backend boot emits InsecureKeyLengthWarning: The HMAC key is 31 bytes long, which is below the minimum recommended length of 32 bytes for SHA256.

Cause. The default value of jwt_secret in backend/app/core/config.py:21 is the literal string "change-me-jwt-secret-set-in-env" — thirty-one characters. In dev, that default is what gets used.

Fix. Bump the default to a ≥32-byte string, or — better — refuse to start in production when the default is in use. Combined with the secret_key = "change-me-in-production" default at config.py:26, a single "fail-fast on default secrets" assertion at startup would close both sharp edges in one line.

Issue 3 — Pydantic field-shadow warnings (cosmetic, noisy)

Symptom. Three startup warnings: UserWarning: Field name "copy" in "ScheduledPostCreate" / "ScheduledPostUpdate" / "ScheduledPostRead" shadows an attribute in parent "BaseModel".

Cause. The three Pydantic schemas in backend/app/api/v1/scheduled_posts.py declare a field literally named copy (as in "ad copy"), which shadows BaseModel.copy().

Fix. Rename the field to body (or post_copy) with a Pydantic Field(..., alias="copy") so the JSON shape doesn't break. ~6 lines, no migration.

Issue 4 — Anthropic + Resend keys unset (expected in dev)

Symptom. /health/dependencies returns all_ok: false with detail "anthropic_api_key unset" and "resend_api_key unset".

Cause. Neither key is provisioned in the dev .env.

Fix. Documented and intentional. The dependency health endpoint correctly reports the dev stack is missing these. Production deployments set both via secret management. No change needed.

Summary

Net. One cosmetic healthcheck failure, one weak default JWT secret, three Pydantic field-shadow warnings, two expected unset keys. No outage; no user-visible defect. All four cosmetic findings are sub-30-minute fixes and would fit cleanly into a single "infra polish" PR before the v1.2.0 cut.

CI/CD shape (post-Sprint 4)

The platform recently moved (PR #343, #345) from a cloud CI model to a local-gate model:

  • Local pre-push gate. docker compose exec backend pytest -q and docker compose exec frontend npm run build are run by the developer before git push; pass/fail is noted in the commit body.
  • GitHub does only auto-merge. A poller workflow watches PRs labelled auto-merge; when the claude-review check returns and the rollup is clean, it squash-merges.
  • Instant trigger. The poller fires on workflow_run: ["Claude Code Review"] so the gap between review-completion and merge is ~10 seconds for docs-only PRs and ~1 minute for code PRs.
  • Cron fallback. Tightened to every 1 minute (GitHub Actions floor) to catch missed triggers.

  • No load tests. The platform has not been measured under sustained agent-run load.
  • No security review automation. Manual /security-review available on demand.

Chapter 12

Path Forward — Observations, Not Prescriptions

This chapter is observational. It does not recommend a roadmap; PLAN-v1.2 does that. It catalogues the moves that, given the current state, would have outsized impact for low effort.

The smallest move that closes the most loops

A single "infra polish + v1.2.0 cut" PR would close Chapters 9, 10, and 11 simultaneously. It would:

  1. Set ENV HOSTNAME=0.0.0.0 in frontend/Dockerfile → green healthcheck.
  2. Bump the jwt_secret default and add a startup fail-fast for default secrets in production.
  3. Rename the copy field on the ScheduledPost* schemas → silence three Pydantic warnings.
  4. Add a .git/hooks/pre-push stub that runs the local test gate.
  5. Move the [Unreleased] changelog block under ## [1.2.0].
  6. Cut the v1.2.0 release with title v1.2.0 per the release-name-equals-tag rule.
  7. Generate the Sprint 5 status report using the canonical three-segment template.

Total estimated effort: ~2 hours. Output: a clean, tagged, hygienic v1.2.0 with a written status report.

The next single biggest user-visible win

Surfacing the Model Registry's ModelCallLog metrics — already logged per-call with USD costs — as a 7-day cost-by-model chart on /admin/models. The data is there; the visualization is missing. This turns the registry from "configured" to "instrumented" and gives the operator a believable answer to "what is this platform spending."

The next single biggest engineering win

Wiring GET /agents/runs/{request_id}/trace into the Inbox / approval view. The endpoint exists; the frontend consumer does not. With it, a reviewer can see exactly what a role-agent thought, what tools it called, in what order, before deciding to approve. The 4-eye rule becomes a real review, not a checkbox.

The next single biggest commercial win

Closing marketing issues #49 (one-pager), #50 (slides), and #52 (demo video recording). Without these, the platform's capability outpaces its presentability. Engineering does not own these; an owner outside engineering needs to be assigned.

The strategic question

The one decision worth taking seriously — and the one most likely to be deferred — is whether the platform should remain a marketing OS or whether the underlying agent ops substrate is the product. The repository now has enough of an answer to make that conversation productive; the parked analysis is in TEMP-pivot-discussion.md. Whatever the outcome, the question should not stay open into Sprint 6.

What is explicitly not recommended

  • A green-field refactor of the service layer. The 51 services are functional; refactoring them today is busywork.
  • Adding new providers to the Model Registry. 26 provider types are already declared. The bottleneck is not provider count; it is real wiring.
  • Adding new MCP adapters before the existing 14 have a deployed customer using them. Surface-area without a tenant is shelfware.
  • A second Conductor pass before the first one ships in v1.2.0. S5-CDR-F polish is the right stopping point.
Closing observation. The project is in better shape than its open-issue count suggests. Five sprints, four releases, two-thirds of a real product, and a substrate that quietly outgrew its original frame. The next move is small and obvious; the move after that is large and strategic.
