What landed

  • Two-tier admin model — single bootstrap superadmin (s-admn-000000), per-org admins; centralized guards, last-admin protection, self-demote refusal, audit trail, in-app notifications on role changes. is_superuser=True creation is refused for anyone but the bootstrap account.
  • Universal slug scheme — users u-{first4}-{6hex}, orgs o-{first4}-{6hex}, bootstrap hardcoded. Migration re-slugs every existing row.
  • Left-sidebar navigation — replaces the top bar; pages group by domain. Admin lives in its own collapsible section.
  • Create-user-with-org dialog — superadmin can create a user + assign them to multiple existing orgs + create new orgs inline, all from one form.
  • Auto-merge + auto-close pipeline — the queue drains end-to-end. Squash merges now carry the PR body to the merge commit; the workflow has issues: write; Closes #N actually closes #N.
  • The entire SP3-1 → SP3-24 polish lane — tabbed Org-detail, project-setup wizard, Fernet-encrypted social tokens, knowledge drill-down, hooks lab, A/B variant studio, repurposing engine, content heatmap, BYO MCP marketplace, kanban, time tracker, retainer + invoices, magic-link sign-in.

What didn't land (deferred by design)

  • Marketing collaterals — one-pager, slides, demo script, demo video, launch posts (issues #49–#53). Owned out-of-band by the operator; engineering does not touch the marketing/ tree.
  • TOTP UX — backend columns shipped, but the enrollment flow is Sprint 4 scope.
  • Real OAuth credentials — the OAuth scaffold is live; per-provider client-id/secret population is operator-side and not a code-shipping task.

Top three takeaways

1. The platform is now operable.

An admin can create users, assign them to orgs, reset their passwords, and audit every action — without touching the database. That was missing in v1.1.0 and is the single biggest unblock for the v1.2 demo.

2. The CI/CD pipeline runs itself.

Open a PR with Closes #N and the auto-merge label. CI passes → bot squashes → issue auto-closes → board flips to Done. No human in the loop. We exercised the pipeline forty-plus times this sprint.

3. The version line now matches the plan doc.

The roadmap is PLAN-v1.2.md; releases were misaligned at v0.1.0-mvp/v0.2.0. Renamed to v1.0.0 / v1.1.0 / v1.1.1 so the stakeholder sees one coherent version line through to the v1.2 demo.

+ Sprint 4 opens with: Brand Studio polish, real OAuth wiring, observability dashboards.

Chapter 3

Project Intent & Target Audience

3.1 What DClaw Marketing is

DClaw Marketing is an agent-driven marketing operating system. A small team — or one operator plus AI agents — runs a full marketing function. Humans set the brand kit and feed in source material; AI agents draft content, schedule posts, run ads, surface analytics, and propose actions. Humans supervise from their Station and approve outbound actions in an Approval Inbox. Agents never publish without consent.

The system is multi-tenant by design (Organization → Project → Asset hierarchy), brand-aware (versioned BrandKit injected into every prompt), knowledge-grounded (ingestion → embeddings → KG with write-back insights), and audit-traced end-to-end. Every cost is metered; every action is logged.

3.2 The people we're building for

The Solo Operator

A founder, consultant, or in-house marketer running marketing for a single business. Needs the full stack but can't justify a 5-person team. DClaw acts as their force multiplier.

The Boutique Agency

2–10 people serving multiple clients. Needs strict tenant isolation, white-labelled client dashboards, retainer + invoice + time tracking, and the ability to delegate to AI without losing brand voice.

The In-House Marketing Function

A growing company's marketing team. Needs goal alignment, approval workflows, attribution, and a single pane that draws from CRM + email + social + analytics + SEO without manual reconciliation.

3.3 Differentiators

  • Approval-first. Every outbound action ends in an Approval Inbox before going out.
  • Brand-conditioned generation. The BrandKit and the KG write-back insights are injected into every prompt — agents inherit the brand voice automatically.
  • MCP-first integrations. 14 concrete adapters + BYO MCP marketplace; no bespoke per-integration code.
  • Self-hosted by default. Docker Compose stack; the operator owns the Fernet master key and can swap LLM providers at any time.
  • Auditable. Every admin action, agent run, and outbound publish is recorded in audit_events with the actor, the target, and the payload.

3.4 What "v1.2 demo" looks like — and where we landed

The stakeholder reads PLAN-v1.2.md and expects a v1.2.0 release. After Sprint 3 we are materially in that posture: every backend the demo needs exists; the operator can drive the platform end-to-end; the version line aligns. The remaining Sprint 4 work is presentation (Brand Studio polish, real OAuth credentials, observability dashboards) rather than core platform.

Chapter 7

Theme-by-Theme Detailed Status

Sprint 3 was organized around themes rather than PLAN-v1.2 phases (which were already substantively complete). This chapter takes each Sprint 3 theme and describes what shipped, what tests cover it, and what's left.

A Admin Model & Identity 100%

The single biggest structural change of the sprint. v1.1.0 treated every is_superuser=True account as a god account; there was no per-org admin role, no last-admin protection, and no human-readable identifier on users or orgs.

What shipped

  • Bootstrap superadmin — single hardcoded account admin@dclaw.io with slug s-admn-000000 and full_name "DClaw SuperAdmin"; re-asserted on every backend startup; cannot be deleted; the only path to recover is the operator-held Fernet master key.
  • Per-org admins — OrganizationMembership.role = admin grants full control of a single org. Org admins can invite, remove, change role, reset password — only within their own org(s).
  • Centralized guards — every admin-only endpoint goes through one require_org_admin() dependency; non-bootstrap superadmin creation is refused at the API layer (returns 409).
  • Last-admin protection — the system refuses to demote, revoke, or remove the final admin of an org. Returns 409 with a clear message.
  • Self-demote refusal — admins cannot demote themselves to manager or viewer; must be performed by another admin or a superadmin.
  • Audit + notify — every admin action writes an audit_events row and posts an in-app notification to the affected user.
  • Slug scheme — users u-{first4}-{6hex}, orgs o-{first4}-{6hex}, bootstrap fixed. Migration re-slugs every existing row.

Tests

backend/tests/test_admin.py + backend/tests/test_orgs.py cover: temp password issue, duplicate-email refusal, superadmin-creation refusal (409), org create + slug shape, two-orgs-same-name slug uniqueness, member add / remove / role-change, password reset, cascade on org delete with audit row survival.
